엔진 선택과 멀티플레이 준비 — v0.8.0
검토일: 2026-10-12

현재 게임은 브라우저에서 실행하는 웹게임이 맞습니다. 다만 원하는 턴제 탐험 RPG의 조작과 연출을 웹에서도 만들 수 있습니다. 이번 지도 중심 화면 개편에는 Unity나 Godot 설치가 필요하지 않습니다. 화면 구성, 직접 대상 선택, 행동 결과의 연속 처리부터 완성한 다음, 본격적인 캐릭터·환경 연출을 만들 때 표시용 엔진을 선택하는 것을 권합니다.

확인한 현재 구조
- hunt-engine.js는 create, dispatch, assertState, exportSave, importSave를 제공하며 규칙·상태·명령 기록을 관리합니다. dispatch는 이전 상태를 복사해 명령을 처리하고 상태를 검증한 뒤 revision과 명령 기록을 갱신합니다.
- importSave는 초기 조건과 명령을 다시 실행해 저장 상태가 동일한지 검사합니다. 이 저장 검증을 유지해야 합니다.
- hunt-app.js는 명령을 전달하고 지도·손패·무기·임무·적 등을 DOM에 표시합니다. 규칙 모듈과 표시 모듈이 이미 나뉘어 있으므로 화면을 바꾸려고 규칙 전체를 다른 언어로 다시 작성할 필요는 없습니다.
- 현재 규칙은 싱글플레이를 기준으로 구현됐습니다. activeHunterId 확인이나 명령 기록이 있다고 해서 멀티플레이가 완성된 것은 아닙니다.

선택지와 비용

1. 지금의 웹 기술로 UI/UX를 개편 — 현재 단계의 권장안
   장점: 기존 규칙과 저장 형식을 유지하면서 고정 HUD, 지도 직접 선택, 행동 예고, 모달 이야기, 전투 피드백을 빠르게 개선할 수 있습니다. 별도 게임 에디터 설치가 필요하지 않습니다.
   비용: 지도 확대·이동, 애니메이션, 효과·음향의 타이밍과 입력 잠금은 직접 구성해야 합니다. 독자 삽화와 캐릭터 표현을 만드는 작업은 그대로 필요합니다.
   적합한 시점: 이번 지도 중심 화면, 다음 대상 선택·전투 흐름 개편.

2. 규칙은 유지하고 Phaser를 지도·연출 계층에 추가 — 2D 연출 단계의 우선 후보
   Phaser는 JavaScript/TypeScript 기반의 2D 웹 게임 프레임워크이며 Canvas/WebGL 표시, 카메라, 입력과 애니메이션을 제공합니다. 일반 프로그램처럼 Unity 에디터를 설치하는 방식이 아니라 프로젝트에 라이브러리를 추가하는 방식입니다. 공식 설명: https://docs.phaser.io/phaser/getting-started/what-is-phaser
   장점: 지금의 JavaScript 규칙을 재사용하면서 캐릭터 이동, 공격 효과, 카메라 확대·이동, 마우스·터치 입력을 구성할 수 있습니다. 카메라 기능: https://docs.phaser.io/phaser/concepts/cameras / 입력 기능: https://docs.phaser.io/phaser/concepts/input
   비용: 지도 표시를 Canvas로 옮기는 작업과 좌표·선택·접근성·HUD 연결이 필요합니다. 멀티플레이 서버는 별도로 개발해야 합니다.
   적합한 시점: 독자 타일·캐릭터·공격 연출의 스타일을 정하고 한 구역에서 이동과 전투 연출을 비교하는 단계.

3. Unity 또는 Godot로 클라이언트를 이전 — 배포·표현 요구가 확정된 뒤 판단
   장점: 에디터의 장면·캐릭터·애니메이션 제작 흐름을 활용할 수 있습니다. Unity는 2D 타일·스프라이트·애니메이션도 지원하므로 3D 게임만을 위한 선택지는 아닙니다. 공식 2D 문서: https://docs.unity.com/en-us/engine/6000.0/manual/unity2d
   비용: 새 클라이언트 구축, 입력과 UI 재작성, 자산 변환, 빌드·배포 관리가 필요합니다. 규칙을 C# 또는 GDScript로 옮기면 저장·재현·기존 사례에 대한 동등성 검증도 다시 필요합니다. 기존 규칙을 서버에 유지하고 새 클라이언트가 명령과 결과만 주고받는 방식도 가능하지만, 오프라인 솔로 실행 방식은 별도 설계해야 합니다. 이 비용 비교는 현재 코드 구조를 보고 내린 개발 판단입니다.
   제약: Unity의 웹 빌드도 브라우저의 네트워크 제약을 따르며, 엔진 설치만으로 온라인 세션이 생기지 않습니다. https://docs.unity3d.com/Manual/webgl-networking.html
   Godot의 현재 안정 문서는 Godot 4 C# 프로젝트의 웹 내보내기를 지원하지 않는다고 설명합니다. 브라우저 배포를 유지한다면 언어 선택부터 확인해야 합니다. https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html
   적합한 시점: 3D·입체 카메라가 핵심 요구로 확정되거나, 독립 실행 파일 중심의 제작·배포 흐름을 우선하려는 경우. 브라우저에서 실행된다는 이유만으로 지금 이전할 필요는 없습니다.

추후 멀티플레이에서 필요한 일
권장 구조는 클라이언트가 이동·공격·회피 등의 의도를 보내고, 서버가 명령의 유효성과 차례를 확인해 규칙을 실행한 뒤 결과를 배포하는 방식입니다. 서버가 최종 상태를 결정하는 구조는 엔진과 별개인 설계 선택입니다. Unity의 서버 권한 설명: https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.7/manual/terms-concepts/authority.html

추후 사용자가 멀티플레이 개발을 요청하면, 여러 사냥꾼의 규칙, 접속·방·권한, 순서와 중복 명령 처리, 동시 반응 선택, 숨겨진 정보의 배포 범위, 진행 저장과 재접속을 구현하고 검사해야 합니다. 현재의 revision·명령 기록·규칙 모듈은 활용할 수 있는 기반이며, 이 항목들이 지금 구현됐다는 뜻은 아닙니다. 기존 저장 파일 재생 검증은 온라인 권한 검사나 치트 방지 기능을 대신하지 않습니다.

현재 결정
이번 개편은 현재 규칙 엔진을 유지한 채 진행합니다. 엔진 설치 요청은 없습니다. 지도·행동·전투 조작을 먼저 완성하고, 독자 시각 자산과 움직임을 실제로 넣는 시점에 Phaser를 이용한 한 구역 시제품을 검토합니다. Unity/Godot 이전이 유리해지는 요구가 확인되면, 필요한 설치와 기존 규칙·저장 데이터의 유지 방식을 먼저 구체적으로 안내합니다.
